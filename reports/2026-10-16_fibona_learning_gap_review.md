## 2. Fibona 的核心，及证据边界

用户提供的 `/fibona-agent` 为在线应用入口，未登录看到登录页。研究转向官方公开技术报告和官方仓库。只下载阅读源码，未执行其 Agent、安装其依赖或把 Lobuddy 数据交给它。

源码版本：`FibonaAI/fibona-agent@7ed2040bfbc476d78bc522dbdd3f796192e3166c`。

- [官方技术报告](https://fibona.ai/blog/fibona-agent)：核心思路是由模型编写每一步程序，并自行组织下一次调用的输入；失败后进入恢复步骤。
- [Python 核心](https://github.com/FibonaAI/fibona-agent/blob/7ed2040bfbc476d78bc522dbdd3f796192e3166c/core/agent.py)：`Mind` 固定核心调用约束；`Slot` 接收下一段代码并在本轮结束后关闭；`Memory` 保存原始执行记录；`Agent.run` 执行和恢复。
- [执行环境](https://github.com/FibonaAI/fibona-agent/blob/7ed2040bfbc476d78bc522dbdd3f796192e3166c/core/env.py)：同进程 IPython，变量跨 cell 保留；异常保留现场，不自动回滚副作用。代码自身说明卡死或解释器崩溃会带走 Agent。
- [可修改的上下文组织](https://github.com/FibonaAI/fibona-agent/blob/7ed2040bfbc476d78bc522dbdd3f796192e3166c/bootstraps/terminal/context.py)：工作指令、上下文构建器、变量说明、原始目标、约束、已验证完成和待办均显式存在；模型能改外围策略。
- [Electron 实验说明](https://github.com/FibonaAI/fibona-agent/blob/7ed2040bfbc476d78bc522dbdd3f796192e3166c/experiments/electron/README.md)：生成的 JavaScript 在主进程运行，可访问 Node/Electron；通过 history.jsonl 与 boot.js 跨启动保留行为，连续三次启动失败将 boot.js 隔离。

抽象成：**稳定的核心约束 → 模型生成下一步代码 → 保留状态并执行 → 记录结果/错误 → 自选下一次上下文 → 继续或修复。**

这是一种让运行策略可变的架构，并不是 EXP 升级，也没有通过这里的代码证明模型权重变强或具有主观意识。已读核心没有通用的候选版本对照评测与“更好才晋升”机制；“能改自己”与“改后质量更好”需要分别证明。

版本差异必须保留：技术报告的伪代码与当前实现不完全一致。当前 Python Slot 同一 cell 最后提交生效，关闭后拒绝迟到提交；Python 恢复循环未设置固定次数上限，而桌面实验在恢复 cell 再失败时退出。桌面 boot.js 的三次启动保护是另一个机制。不能将网页上的“三次”套到所有路径。

## 3. 能力对照

| 核心问题 | Fibona 所提供 | Lobuddy 已有 | 缺口或选择 |
|---|---|---|---|
| 稳定身份与可变实现 | 核心 Mind/调度约束固定，外围程序可改 | DSH + 插件桥 + Python 权威业务层 | 现有治理边界适合保持；目前没有开放自修改业务实现 |
| 如何安排下一步 | 模型提交完整程序 cell | DSH 循环选择受控工具；前后台独立会话 | 尚无持久化的结构化目标/约束/已完成/待办工作状态供策略更新 |
| 怎样用过去 | 执行代码、输出、错误与变量；代码决定输入 | SQLite 记忆、FTS 历史检索、摘要、上下文预算 | 用户画像与技能选择仍较固定；失败到经验缺乏闭环 |
| 如何学习技能 | 可生成代码、工具和新的工作方式 | 技能 CRUD、版本号、投影、候选、成功失败统计 | 候选主要模板提取；缺试运行、质量对照和版本晋升/回退 |
| 出错怎么办 | 保留现场，恢复 cell 生成修复 | 进程/断连恢复、取消、安全拒绝、结算幂等 | 有可靠停止和恢复边界，缺业务层“诊断→修复方案→验证→经验” |
| 如何证明变好 | 已读核心没有通用质量晋升闸门 | task completed 驱动奖励和技能成功统计 | 双方都不能仅凭循环正常结束证明任务真正成功；Lobuddy 应新增验证层 |
| 陪伴 | 通用可编程 Agent，不直接等价于陪伴产品 | 浊蒂外形、语音、专注、主动策略、相处偏好 | 产品方向已明确，重点补记忆质量、反馈学习与主动内容相关性 |

| FG-07 / P2 | 技能自动候选当前关闭；提取器按工具名及截断输出生成 Markdown；只有成功路径调用 | 用户可显式建技能，尚无持续自改进；失败难以变成反例 | 有价值事件才生成候选，包含条件/步骤/输出验证/失败反例；加入去重、预算、版本评测和晋升 | 常见任务越做越可靠，失败不反复发生 | 错误模板复用 / 测试泄漏与成本；先人工批准候选 |
| FG-08 / P2 | 当前主桥关闭任意插件安装与未治理工具；无可变工作流的隔离执行和晋升机制 | 受控执行可靠，但不能像 Fibona 动态搭建新能力 | 在 DSH 上增加可审计的候选工作流/工具扩展，独立进程与权限边界、限额、测试环境、版本回退；审批/密钥/网关留在不可自改层 | 能扩展能力而不破坏桌宠及业务数据 | 扩展性受限 / 任意代码与副作用风险；进程隔离本身不等于沙箱 |

“至少三次证据并确认才把习惯当偏好”目前主要是上下文指令，网关还没有独立证据条数/用户确认字段验证；补 FG-01 时应实现结构约束。当前手动相处设置同一 kind 使用固定 ID，属于一个可修改偏好槽，不能当成完整、多条、有时间线的关系记忆模型。

能力解锁目前有门槛、记录和显示；在本次检查的新服务/桥调用链中，未发现这些解锁逐项开启专属新执行实现的映射。应列入 FG-04/08 的能力清单，避免“多任务未解锁”与已经可用的前后台任务设计互相矛盾。

## 5. 建议顺序与验收

保留当前 DSH 架构，在其上引入 Fibona 的“稳定核心、可变外围、带证据的工作状态和修复”思想。现在整体再换引擎并不能直接补齐关系记忆与评测；当前最明显的缺口位于业务学习层。

| 建议阶段 | 范围/代价 | 具体交付 | 验收要求（均待实施） |
|---|---|---|---|
| A：让记忆真实可用 | FG-01/02/03；中等，增加模型提取调用与调度 | 运行状态页、设置接线审计、交流候选、结构化摘要、来源/撤销 | 改称呼后跨会话生效；一次情绪不固化；删除后检索/投影/上下文同步；后台维护执行/失败可查 |
| B：让陪伴随相处变化 | FG-04/05；中等，内容策略与面板调整 | 多条偏好/共同经历、话题候选、反馈时间线；保留旧 EXP | 主动话题可追溯共同经历；忽略冷却保持；中文偏好体现于表达；明确纠正覆盖旧倾向 |
| C：让技能经过验证成长 | FG-06/07；较高，需要验收规则与固定评测集 | 执行证据、失败经验、候选试用、旧新版对照、晋升与回退 | 没产物不能算已验证成功；失败候选不替换稳定版本；新技能通过回归且改善目标指标；停用立即不注入 |
| D：受控可编程工作流 | FG-08；高，隔离与权限是主要成本 | DSH 可调用的版本化工作流执行器；可审查变更和有界修复 | 修复不得重放未知副作用；超预算停止；崩溃回到稳定版；不能修改审批/凭据/记忆网关；对照评测通过再启用 |

建议先 A+B，再 C；D 等出现普通技能无法表达的真实需求后实施。C 的验证模型与测试框架应先于 D 的自修改权限。每个阶段仍按项目既有纪律独立验收并中文提交；不自动替代当前 P8/P9 计划。

更贴近你的首批验收样例：记得喜欢的称呼和台妹声音；被明确指出回复太长后后续简短；回忆真实一起完成的专注；主动邀请被忽略后保持安静；重复一个文件整理任务时按验证过的步骤做，失败后记住原因。这里“知道选定声音”还应来自已配置音色等运行能力摘要，而非假设所有设置自动出现在模型上下文。
